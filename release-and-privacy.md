# Release and privacy

Keep three deliverables separate:

- Working project: may contain private photographs and drafts; keep local or restricted.
- Deployment folder: runtime HTML/CSS/JS, images and audio only; omit backups, helper scripts and debugging screenshots.
- Public skill portfolio: reusable instructions, anonymous cases and authorized example material; not a copy of the private website.

Before describing an upload as safe to publish, inspect the actual files. An ignore rule does not scrub files already uploaded or committed. Raw photographs, embedded base64, image metadata, real names, private letters, local usernames, credentials and third-party character art may all need separate treatment.

Verify relative paths, referenced files and filename case in the deployment folder. Case-insensitive local testing can miss failures on a case-sensitive host.

A name-entry story gate is not access control. If private hosting is required, protect both pages and asset requests with hosting/server-side authentication. Do not advertise JavaScript password checks as secure protection for readable static media.

Published, public and private are different concepts. Check a provider's current rules before explaining plan limits or changing visibility. Do not silently change a private project to public to solve access issues.

For a portfolio case study, distinguish user creative direction, AI-assisted work, third-party dependencies, verified behavior and remaining limitations. Include licenses/attribution appropriate to the actual content. Do not invent user testing, adoption statistics or performance improvements.
